# Архитектура проекта

## 1. Общая идея

CLI Task Manager разделён на логические части с отдельными зонами ответственности:

1. модель задачи;
2. бизнес-логика работы с задачами;
3. хранилище данных;
4. CLI-интерфейс;
5. точка запуска приложения.

Такое разделение позволяет отделить взаимодействие с пользователем и хранение данных от правил работы с задачами.

## 2. Модель задачи

Модель представляет сущность `Task` в виде `dataclass` со следующими данными:

- `id`;
- `title`;
- `priority`;
- `deadline`;
- `status`;
- `created_at`.

Предварительные типы полей:

| Поле | Тип |
| --- | --- |
| `id` | `int | None` |
| `title` | `str` |
| `priority` | `int | None` |
| `deadline` | `date | None` |
| `status` | `str` |
| `created_at` | `datetime` |

Для статуса используются обычные строки. Допустимые значения статуса ограничены значениями `todo`, `in_progress` и `done`.

Новая задача до сохранения в хранилище может не иметь идентификатора (`id = None`). После сохранения SQLite создаёт для неё целочисленный идентификатор.

В модели могут находиться простые правила, относящиеся непосредственно к задаче:

- допустимые значения статуса;
- допустимые значения приоритета;
- определение просроченности задачи.

Модель не отвечает за пользовательский интерфейс и непосредственную работу с хранилищем.

## 3. Бизнес-логика

Бизнес-логика выполняет основные операции приложения:

- создание задачи;
- удаление задачи;
- изменение статуса;
- получение списка задач;
- фильтрацию;
- сортировку.

Она работает с моделью `Task` и использует хранилище для получения и сохранения данных. CLI не реализует эту логику самостоятельно.

## 4. Хранилище данных

Хранилище отвечает только за сохранение и загрузку задач. Для MVP планируется использовать SQLite.

Хранилище предоставляет бизнес-логике возможность:

- сохранить задачу;
- получить задачи;
- обновить задачу;
- удалить задачу.

Хранилище не содержит бизнес-правила: например, не определяет допустимость статуса и не выбирает способ сортировки задач.

Хранилище преобразует данные SQLite в объекты `Task` при загрузке и объекты `Task` в данные SQLite при сохранении. Детали этого преобразования относятся к реализации хранилища.

## 5. CLI-интерфейс

CLI отвечает за взаимодействие пользователя с приложением. Он должен:

- показывать главное меню;
- получать пользовательский ввод;
- запрашивать данные для создания задачи;
- запрашивать `id` задачи;
- показывать список задач;
- выводить сообщения об ошибках;
- запрашивать подтверждение действий.

CLI не обращается к SQLite напрямую и не реализует основную бизнес-логику самостоятельно.

## 6. Точка запуска

Точка запуска создаёт необходимые компоненты приложения, связывает их между собой и запускает CLI.

Она не содержит основную бизнес-логику.

## 7. Направление взаимодействия

Основной поток взаимодействия:

```text
Пользователь → CLI → бизнес-логика → хранилище
```

Модель `Task` используется бизнес-логикой и хранилищем как основное представление задачи. CLI не обращается к хранилищу напрямую.

## 8. Предварительная структура проекта

```text
cli-task-manager/
├── src/
│   └── task_manager/
│       ├── __init__.py
│       ├── models.py
│       ├── service.py
│       ├── storage.py
│       ├── cli.py
│       └── main.py
├── tests/
├── docs/
│   ├── requirements.md
│   └── architecture.md
├── README.md
├── pyproject.toml
└── .gitignore
```

Назначение файлов:

| Файл или каталог | Назначение |
| --- | --- |
| `models.py` | Модель `Task` и связанные с ней сущности. |
| `service.py` | Бизнес-логика приложения. |
| `storage.py` | Работа с хранилищем. |
| `cli.py` | Интерактивный консольный интерфейс. |
| `main.py` | Точка запуска приложения. |
| `tests/` | Автоматические тесты. |

## 9. Архитектурные принципы

- Каждый модуль имеет понятную ответственность.
- CLI не работает напрямую с базой данных.
- Хранилище не содержит бизнес-логику.
- Точка запуска не содержит бизнес-логику.
- Архитектура остаётся простой и не содержит лишних абстракций.
- Новые слои и паттерны добавляются только при реальной необходимости.
